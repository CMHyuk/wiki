# Thread Dump는 보통 어떤 상황에서 분석하나요?

> 2026-08-06 · 데일리 면접 질문

## 답변

Thread Dump는 **특정 시점에 JVM 안 스레드들의 상태와 stack trace를 찍은 스냅샷**입니다. 어떤 스레드가 지금 어떤 코드를 실행 중인지, 무엇을 기다리며 멈춰 있는지를 그대로 보여주기 때문에, 로그에는 아무 에러도 없는데 서비스가 이상하게 동작하는 상황에서 JVM 내부를 들여다보는 1차 도구로 사용합니다.

제가 Thread Dump를 꺼내 드는 상황은 크게 네 가지입니다. 첫째, **API 응답이 갑자기 느려지거나 아예 응답이 없을 때**입니다. 에러가 나면 로그에 남지만, 스레드가 어딘가에서 하염없이 기다리는 중이면 로그에는 아무것도 안 찍히기 때문에 덤프로 스레드가 어디에 멈춰 있는지 직접 봐야 합니다. 둘째, **CPU 사용률이 비정상적으로 높을 때** 어떤 스레드가 CPU를 태우고 있는지 찾기 위해서입니다. 셋째, **thread pool 고갈이 의심될 때** — 톰캣 워커 스레드가 전부 바쁘다고 나오는데 처리량은 안 나오는 상황에서, 그 스레드들이 실제로 무엇을 하고 있는지 확인합니다. 넷째, **deadlock이 의심될 때**입니다.

덤프를 찍는 방법은 `jstack <pid>`, `jcmd <pid> Thread.print`, 또는 프로세스에 `kill -3`(SIGQUIT)을 보내는 방식이 있습니다. `kill -3`의 덤프는 명령을 친 터미널이 아니라 JVM의 표준 출력으로 나간다는 점을 알아야 하고, Spring Boot Actuator를 쓴다면 `/actuator/threaddump` 엔드포인트로도 받을 수 있습니다(노출 설정과 인증이 전제입니다 — 스택과 클래스명이 그대로 드러나는 정보라 무인증 노출은 위험합니다). 프로세스를 죽이지 않고 수집할 수 있지만, 덤프 순간 JVM이 짧게 safepoint에 멈추므로 완전히 무비용은 아닙니다. 참고로 JDK 21+의 가상 스레드는 jstack 기반 덤프에 다 나타나지 않아서 `jcmd <pid> Thread.dump_to_file`을 써야 합니다.

분석할 때는 먼저 각 스레드의 상태를 봅니다. `RUNNABLE`은 실행 중이거나 실행 대기, `BLOCKED`는 synchronized 모니터 락 진입 대기, `WAITING`/`TIMED_WAITING`은 wait·park·sleep 등으로 스스로 대기에 들어간 상태입니다. 여기서 주의할 점은 `RUNNABLE`이 "CPU를 쓰는 중"과 같은 말이 아니라는 것입니다 — native 코드에서 소켓 읽기처럼 OS 자원을 기다리는 중이어도 JVM 입장에서는 `RUNNABLE`로 표시됩니다. 그다음 **같은 stack trace에 스레드가 얼마나 몰려 있는지**를 봅니다. 수십 개의 워커 스레드가 전부 같은 지점 — 예를 들어 DB 커넥션 획득 대기, 외부 API 응답 대기, 특정 락 획득 — 에 멈춰 있다면 그 지점이 병목입니다. deadlock이 있으면 jstack이 덤프 하단에 "Found one Java-level deadlock" 같은 섹션으로 어떤 스레드가 어떤 락을 잡은 채 어떤 락을 기다리는지 자동으로 정리해 줍니다.

마지막으로 중요한 것은 **덤프를 한 번만 보지 않는다는 점**입니다. Thread Dump는 스냅샷이라서 한 장만 보면 그 순간 우연히 대기 중이었던 것인지 계속 멈춰 있는 것인지 구분할 수 없습니다. 그래서 몇 초 간격으로 3~5회 찍어서 **여러 장에 걸쳐 같은 스레드가 같은 지점에 머물러 있는지**를 비교합니다. 다만 같은 자리에 있다고 전부 문제는 아닙니다 — idle 워커나 정상적인 장기 I/O도 계속 같은 자리에 보입니다. 그래서 덤프 비교는 "요청이 실제로 완료되고 있는가, 큐가 줄고 있는가" 같은 실제 진행 여부와 함께 판단해야 합니다.

## 꼬리 질문

### Thread Dump에서 `BLOCKED`와 `WAITING`은 어떻게 다른가요?

`BLOCKED`는 **synchronized 블록/메서드의 모니터 락에 진입하려는데 다른 스레드가 그 락을 잡고 있어서 못 들어가는 상태**입니다. 스레드가 능동적으로 기다리기로 한 것이 아니라 락 경합에 밀린 것이고, 덤프에는 `waiting to lock <0x...>`으로 대상 모니터가 표시됩니다. 반면 `WAITING`은 **스레드가 스스로 대기에 들어간 상태**로, `Object.wait()`, `Thread.join()`, `LockSupport.park()` 등을 호출해 다른 스레드가 깨워주기를 기다리는 것입니다. `TIMED_WAITING`은 시간 제한이 있는 대기로, `Thread.sleep()`처럼 누가 깨워주는 것이 아니라 시간이 지나면 스스로 깨어나는 경우도 포함됩니다. 참고로 `Object.wait()`에서 notify를 받은 스레드도 모니터를 재획득하기 전까지는 `BLOCKED`로 보일 수 있습니다.

실무에서 중요한 함정은 `java.util.concurrent`의 `ReentrantLock` 같은 락은 내부적으로 `LockSupport.park()`를 쓰기 때문에, **락 경합 중이어도 `BLOCKED`가 아니라 `WAITING`(parking) 상태로 나타난다**는 점입니다. 그래서 "BLOCKED가 없으니 락 경합이 없다"고 판단하면 안 됩니다. 다만 `parking to wait for <0x...>`에 찍히는 주소는 락뿐 아니라 latch, condition, 스레드풀 idle 대기에서도 똑같이 나오므로, 이 표기 하나만으로 락 경합이라고 단정하지 말고 stack trace에서 어떤 코드가 park에 들어갔는지를 함께 봐야 합니다.

### Deadlock 상황에서는 thread state가 어떻게 나타나나요?

synchronized 기반의 전형적인 deadlock이라면 얽힌 스레드들이 `BLOCKED` 상태로, 각자 `locked <A>`를 잡은 채 `waiting to lock <B>`를 표시하며 서로를 순환 대기합니다. jstack은 이 소유-대기 순환을 감지해 덤프 하단에 deadlock 섹션으로 관련 스레드와 락 관계를 정리해 줍니다.

`ReentrantLock` 기반 deadlock도 자동 감지 대상이지만, 스레드 상태가 `BLOCKED`가 아니라 `WAITING`(parking)으로 나타납니다. 이때 `jstack -l`로 ownable synchronizer(보유 중인 j.u.c 락) 정보까지 출력하면 어떤 스레드가 어떤 락을 잡고 있는지 해석하기 쉬워집니다. 주의할 점은 자동 감지가 찾는 것이 **모니터/ownable synchronizer의 소유-대기 순환뿐**이라는 것입니다. 큐·latch·세마포어 대기처럼 락 순환이 아닌 논리적 정지, `tryLock(timeout)` 재시도로 진행이 안 되는 상황은 deadlock 섹션에 잡히지 않으므로, 자동 감지에만 의존하지 말고 여러 덤프에서 진행 없이 멈춰 있는 스레드를 직접 찾아야 합니다.

### CPU 사용률이 높을 때 thread dump와 CPU profiling은 어떻게 함께 보나요?

Thread Dump 단독으로는 "어떤 스레드가 CPU를 쓰는지"가 안 보이므로 OS 지표와 조합합니다. 리눅스라면 `top -H -p <pid>`로 CPU를 많이 쓰는 **스레드의 tid**를 찾고, 그 tid를 16진수로 변환해 덤프의 `nid=0x...`와 매칭하면 해당 스레드의 stack trace를 특정할 수 있습니다(컨테이너 환경이라면 PID namespace가 같은 곳에서 봐야 매칭됩니다). 여러 장의 덤프에서 그 스레드가 계속 `RUNNABLE`로 같은 코드(무한 루프, 비효율적 정규식, 대량 직렬화 등)에 있으면 그 지점을 유력한 원인으로 좁힙니다. 이때 CPU를 쓰는 것이 애플리케이션 스레드가 아니라 **GC 스레드라면 GC 쪽으로 방향을 바꿔야** 하는데, 그렇다고 코드 문제가 아니라는 뜻은 아닙니다 — 과도한 객체 할당 같은 코드 패턴이 GC를 몰아붙이는 경우가 흔하므로 GC 로그로 할당률과 pause를 확인합니다.

다만 이 방식은 스냅샷 몇 장의 조합이라 우연히 같은 지점이 찍혔을 가능성을 배제할 수 없어서, 정밀 분석은 **시간 축으로 샘플링하는 프로파일러**로 넘어갑니다. async-profiler나 JFR(Java Flight Recorder)로 일정 시간 CPU 샘플을 수집해 flame graph로 보면 어떤 메서드가 CPU 시간을 얼마나 점유했는지 통계적으로 나옵니다. 정리하면 thread dump + top으로 범인 스레드를 빠르게 좁히고, 프로파일링으로 메서드 수준까지 확정하는 식으로 함께 씁니다.

### Thread pool 고갈이 의심되면 어떤 stack trace를 확인하나요?

먼저 풀의 워커 스레드 — 톰캣이라면 `http-nio-8080-exec-*` — 를 이름으로 모아서, **몇 개가 살아 있고 각각 무엇을 하고 있는지** 셉니다. 고갈 상황이라면 워커 대부분이 idle이 아니라 어딘가에 멈춰 있고, 보통 같은 지점에 몰려 있습니다. 대표적으로 확인하는 패턴은:

- **DB 커넥션 대기**: `HikariPool.getConnection` → `ConcurrentBag.borrow`에서의 대기 — 커넥션 풀이 먼저 고갈되어 워커가 연쇄로 묶인 상황. 원인은 슬로우 쿼리, 커넥션 누수, 긴 트랜잭션, 풀 사이즈 부족 등이고, HikariCP는 `connectionTimeout`까지 기다린 뒤 예외를 냅니다
- **외부 API 응답 대기**: 구형 JDK라면 `SocketInputStream.socketRead0`, JDK 13+라면 `NioSocketImpl` 계열의 read/park — timeout 미설정이나 과도한 지연으로 워커가 오래 붙잡힌 상황
- **락 대기**: 다수 스레드가 같은 모니터에 `waiting to lock`, 그리고 그 락을 잡은(`locked`) 한 스레드가 무엇을 하고 있는지 추적
- **자체 스레드풀 병목**: 내부 executor의 워커들이 전부 바쁜 상태 — 다만 큐에 작업이 얼마나 쌓였는지는 덤프에 안 보이므로 큐 길이·활성 스레드 수 메트릭을 함께 봐야 합니다

참고로 idle 워커가 `ThreadPoolExecutor.getTask`에서 대기하는 것 — `take()`면 `WAITING`, `poll(timeout)`이면 `TIMED_WAITING` — 은 일감을 기다리는 정상 상태이므로 문제로 오인하면 안 됩니다. 핵심은 "워커가 왜 풀로 돌아오지 못하는가"이며, 몰려 있는 지점이 곧 답입니다.

### Thread Dump만으로 알기 어려운 정보는 무엇이고 어떤 지표를 함께 봐야 할까요?

Thread Dump는 "그 순간 스레드가 어디에 있는가"만 보여주기 때문에 다음이 빠져 있습니다.

- **메모리/힙 상태**: 객체가 무엇으로 차 있는지, 누수가 있는지는 안 보입니다 → heap dump(`jmap`, `jcmd GC.heap_dump`)와 MAT 같은 분석 도구
- **GC 동작**: GC가 얼마나 자주, 얼마나 오래 멈추는지는 안 보입니다 → GC 로그, `jstat -gcutil`, JFR. 응답 지연의 원인이 스레드가 아니라 GC pause인 경우가 많습니다
- **CPU 시간의 정량 정보**: 덤프는 시점 자료라 어떤 코드가 CPU 시간을 얼마나 썼는지 못 봅니다 → async-profiler/JFR 샘플링
- **시계열 추이**: 문제가 언제부터 어떻게 악화됐는지는 스냅샷으로 알 수 없습니다 → APM이나 Micrometer + Prometheus/Grafana 같은 메트릭(요청 지연 분포, 활성 스레드 수, 커넥션 풀 사용률, 큐 대기)
- **OS/외부 요인**: 디스크 I/O 포화, 네트워크 지연, 다른 프로세스의 CPU 점유 → `top`, `vmstat`, `iostat` 등 OS 지표
- **가상 스레드**: JDK 21+에서 가상 스레드를 쓴다면 전통적인 jstack 덤프에는 다 안 나오므로 `jcmd Thread.dump_to_file` 같은 새 방식이 필요합니다

그래서 실제 장애 분석에서는 메트릭으로 "언제부터 무엇이 이상한지" 범위를 좁히고, thread dump로 "지금 스레드가 어디 멈춰 있는지"를 확인하고, 필요하면 heap dump나 프로파일링으로 파고드는 식으로 도구를 조합합니다.

## 한 줄 요약

Thread Dump는 특정 시점 JVM 스레드들의 상태와 stack trace 스냅샷으로, 응답 지연·CPU 급증·thread pool 고갈·deadlock 의심 상황에서 스레드가 어디에 멈춰 있는지 확인하는 도구다. 한 장이 아니라 몇 초 간격으로 여러 장을 찍어 같은 지점에 머무는 스레드를 실제 진행 여부와 함께 판단하는 것이 핵심이고, 메모리·GC·시계열 정보는 heap dump·GC 로그·메트릭을 함께 봐야 한다.
