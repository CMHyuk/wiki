# 인덱스를 많이 만들면 어떤 단점이 있나요?

> 2026-07-23 · 데일리 면접 질문

## 답변

인덱스는 조회 성능을 위해 원본 테이블과 별개로 유지하는 정렬된 자료구조(대부분 B-tree)입니다. 그래서 "공짜로 얻는 조회 최적화"가 아니라, **읽기 성능을 쓰기 비용과 저장 공간으로 사는 trade-off**로 보는 게 정확합니다. 인덱스를 무분별하게 늘리면 이 비용 쪽이 커집니다.

첫째, **쓰기 비용이 늘어납니다.** `INSERT`, `DELETE`는 물론이고 `UPDATE`도 인덱스 컬럼을 건드리면 테이블 데이터뿐 아니라 그 컬럼이 포함된 모든 인덱스를 함께 갱신해야 합니다. 인덱스가 5개 걸린 테이블에 한 건을 넣으면, 힙에 한 번 쓰고 인덱스 5곳의 B-tree를 각각 찾아 들어가 엔트리를 추가하는 일이 벌어집니다. 이 과정에서 페이지가 꽉 차면 **페이지 분할(page split)** 이 일어나 추가 I/O와 단편화가 생기고, 인덱스 페이지에 대한 **락·래치 경합**도 늘어 동시성이 떨어집니다. 쓰기가 많은 테이블일수록 이 비용이 누적됩니다.

둘째, **저장 공간을 계속 소모합니다.** 인덱스는 키 값과 원본 위치(포인터)를 중복 저장하기 때문에, 넓은 컬럼이나 복합 인덱스를 여러 개 두면 인덱스 용량이 테이블 본체를 넘는 경우도 흔합니다. 이건 디스크만의 문제가 아니라, 버퍼 풀/캐시에 올라가야 할 페이지가 늘어나 **정작 자주 쓰는 데이터의 캐시 히트율을 떨어뜨리는** 문제로 이어집니다. 백업·복구 시간도 함께 늘어납니다.

셋째, **옵티마이저의 부담과 오판 가능성이 커집니다.** 후보 인덱스가 많아지면 실행 계획 탐색 공간이 넓어져 계획 수립(파싱/최적화) 비용이 늘고, 서로 비슷비슷한 인덱스가 여러 개 있으면 옵티마이저가 그때그때 통계에 따라 **다른 인덱스를 골라 실행 계획이 요동치기도** 합니다. 잘못 설계된 인덱스는 선택도가 나쁜데도 선택되어 full scan보다 느린 계획을 유도할 수도 있습니다.

넷째, **운영·관리 부담**입니다. 사용되지 않는 인덱스(중복 인덱스, 예전 쿼리를 위해 만들었다가 방치된 인덱스)는 위 비용을 전부 지불하면서 이득은 0인 순수 손실입니다. 인덱스가 많을수록 이런 "죽은 인덱스"가 섞여 들어가기 쉽고, 스키마 변경이나 리인덱싱 작업도 무거워집니다.

정리하면, 인덱스는 많을수록 좋은 게 아니라 **읽기 이득이 쓰기·공간 비용을 넘어서는 것만** 두는 게 맞습니다. 그래서 실제로는 자주 쓰이는 조회 조건·정렬·조인 패턴을 기준으로 필요한 인덱스를 설계하고, 사용량을 모니터링해서 안 쓰이는 인덱스는 걷어내는 방향으로 관리합니다.

## 꼬리 질문

### 인덱스가 INSERT / UPDATE / DELETE에 구체적으로 어떤 비용을 만드나요?

- **INSERT**: 힙에 row를 넣은 뒤, 그 row가 걸린 모든 인덱스에서 키에 맞는 위치를 찾아 엔트리를 추가합니다. 인덱스가 N개면 인덱스 B-tree 탐색·삽입이 N번 일어납니다. 대상 리프 페이지가 꽉 차 있으면 페이지 분할이 발생해 I/O와 단편화가 늘어납니다.
- **DELETE**: 마찬가지로 모든 인덱스에서 해당 엔트리를 찾아 제거(또는 dead 마킹)해야 합니다. MySQL InnoDB나 PostgreSQL은 삭제 즉시 공간을 회수하지 않고 나중에 정리(purge, VACUUM)하므로 그 정리 비용도 인덱스 수에 비례합니다.
- **UPDATE**: 여기가 오해가 많은 부분인데, **변경한 컬럼이 포함된 인덱스만** 갱신됩니다. 인덱스에 없는 컬럼만 바꾸면 인덱스는 건드리지 않습니다. 단, 인덱스 키 컬럼을 바꾸면 "기존 엔트리 삭제 + 새 위치에 삽입"이 되어 사실상 delete+insert 비용이 듭니다. (특히 클러스터형 인덱스 키를 바꾸면 row 자체가 이동하며 나머지 보조 인덱스에도 영향)

공통적으로 인덱스 페이지에 대한 락/래치 경합이 늘어 **동시 쓰기 처리량(throughput)** 이 떨어지는 것도 실무에서 체감되는 비용입니다.

### 사용되지 않는 인덱스는 어떻게 찾나요?

DB마다 사용 통계를 제공합니다.

- **PostgreSQL**: `pg_stat_user_indexes`의 `idx_scan`이 0에 가까우면 조회에 안 쓰이는 인덱스입니다. `pg_stat_statements`로 어떤 쿼리가 실제로 도는지도 대조합니다.
- **MySQL(InnoDB)**: `sys.schema_unused_indexes` 뷰, 그리고 `performance_schema`의 인덱스 사용 통계로 판별합니다.
- **Oracle**: 인덱스 모니터링(`ALTER INDEX ... MONITORING USAGE`)이나 `v$` 뷰로 사용 여부를 추적합니다.

다만 통계 수집 시작 이후 기간만 반영되므로, **월말 배치나 특정 시즌에만 쓰이는 인덱스**를 성급히 지우지 않도록 충분한 관측 기간을 두고, 중복 인덱스(예: `(a)`가 `(a, b)`에 포함되어 선두 컬럼만으로 대체 가능한 경우)부터 정리하는 게 안전합니다. 지우기 전에는 보통 unusable/invisible로 먼저 돌려보고 문제 없으면 drop 합니다.

### 멀티 컬럼 인덱스가 있으면 단일 컬럼 인덱스는 항상 필요 없나요?

아닙니다. **선두 컬럼(leftmost prefix) 규칙** 때문에 그렇습니다.

- `(a, b)` 복합 인덱스는 `WHERE a = ?` 나 `WHERE a = ? AND b = ?` 는 커버하므로, 이 경우 별도의 `(a)` 단일 인덱스는 **중복**이고 지우는 게 맞습니다.
- 하지만 `WHERE b = ?` 처럼 **선두 컬럼 없이 뒤 컬럼만** 조건에 쓰면 `(a, b)` 인덱스를 (사실상) 탈 수 없습니다. 이때 `b`를 자주 단독 조회한다면 `(b)` 인덱스가 별도로 필요합니다.

그래서 "복합 인덱스가 있으니 단일 인덱스는 다 지운다"가 아니라, **선두 컬럼으로 커버되는지**를 기준으로 판단해야 합니다.

### 인덱스를 추가한 뒤 개선 여부는 어떻게 검증하나요?

- **실행 계획 확인**: `EXPLAIN`(가능하면 `EXPLAIN ANALYZE`)으로 의도한 인덱스를 실제로 탔는지, 접근 방식이 full scan에서 index scan으로 바뀌었는지 봅니다. 인덱스를 만들었어도 옵티마이저가 안 쓸 수 있으므로 "만들었다 ≠ 개선됐다"입니다.
- **예상 vs 실제 row 수**: `EXPLAIN ANALYZE`에서 예상과 실제 row 수가 크게 어긋나지 않는지, filesort/temporary 같은 추가 작업이 사라졌는지 확인합니다.
- **양쪽 비용 측정**: 조회 지연시간(latency)만 볼 게 아니라, 그 테이블의 **쓰기 처리량 변화**도 같이 봐야 trade-off를 제대로 평가한 겁니다. 조회는 20% 빨라졌는데 대량 INSERT 배치가 2배 느려졌다면 그 인덱스는 재검토 대상입니다.
- **실 트래픽 반영**: 개발 장비의 소량 데이터가 아니라 운영과 유사한 데이터량·분포에서 측정해야 합니다. 데이터가 적으면 어차피 full scan이 빨라 인덱스 효과가 안 보입니다.

### 조회 성능과 쓰기 성능 중 무엇을 기준으로 trade-off를 판단하나요?

정답이 정해져 있다기보다 **워크로드 특성**으로 판단합니다.

- **읽기 위주(OLAP·조회성 서비스, 게시판 목록/검색 등)**: 인덱스를 적극적으로 두는 게 유리합니다. 쓰기가 드물어 인덱스 유지 비용이 상대적으로 작습니다.
- **쓰기 위주(OLTP·로그/이벤트 적재, 대량 배치 insert)**: 인덱스를 최소화합니다. 필요하면 적재 시점엔 인덱스를 줄였다가 조회 시점에 두는 식으로 분리하거나, 배치 적재 시 인덱스를 잠시 비활성화 후 재생성하기도 합니다.
- **판단 축**: 이 쿼리가 얼마나 자주 실행되고 얼마나 느린가(읽기 이득) vs 이 테이블에 쓰기가 얼마나 자주 일어나고 인덱스가 몇 개인가(쓰기 비용). 이득이 비용을 넘고, 그 조건의 선택도가 좋아 인덱스가 실제로 효과를 낼 때만 추가하는 것이 원칙입니다.

## 한 줄 요약

인덱스는 읽기 성능을 쓰기 비용·저장 공간과 맞바꾸는 자료구조라, 많을수록 좋은 게 아니다. 쓰기마다 관련 인덱스를 전부 갱신해야 하고(페이지 분할·락 경합), 공간과 캐시를 잡아먹으며, 옵티마이저 오판과 죽은 인덱스 관리 부담까지 생긴다. 그래서 실제 조회·정렬·조인 패턴 기준으로 이득이 비용을 넘는 인덱스만 두고, 사용량을 모니터링해 안 쓰는 것은 걷어내는 게 맞다.
