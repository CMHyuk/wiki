# JWT의 signature는 어떤 방식으로 생성되고, 무엇을 보장하나요?

> 2026-08-11 · 데일리 면접 질문

## 답변

JWT는 `header.payload.signature` 구조인데, 정확히는 **JWS(JSON Web Signature)의 Compact Serialization** 형식입니다. signature는 토큰 뒤에 덧붙는 장식이 아니라, 앞의 두 구간이 발급 이후 바뀌지 않았음을 검증하기 위한 값입니다.

서명 대상은 header와 payload를 Base64URL(패딩 없음)로 인코딩해 `.`으로 이은 문자열이고, 이를 **Signing Input**이라고 합니다. 여기서 중요한 건 서명이 JSON 객체가 아니라 **토큰 안에 실제로 들어 있는 그 Base64URL 문자열의 ASCII 바이트열**에 적용된다는 점입니다.

```text
signingInput = ASCII( BASE64URL(UTF8(header JSON)) + "." + BASE64URL(payload octets) )
signature    = BASE64URL( HMAC-SHA-256(secret, signingInput) )   // HS256인 경우
```

그래서 검증할 때도 payload를 파싱해서 다시 직렬화한 값으로 계산하면 안 됩니다. JSON의 공백이나 키 순서만 달라져도 바이트가 달라지고 서명이 깨지기 때문에, 받은 토큰의 두 구간을 **그대로** 다시 서명해서 비교합니다.

signature가 실제로 보장하는 것은 두 가지입니다. 첫째는 **무결성**으로, `userId`나 `role`, `exp` 같은 값을 바꾸면 signingInput이 달라져 검증이 실패합니다. 둘째는 흔히 "발급 주체 검증"이라고 말하지만, 서명 검증만으로 확인되는 건 정확히는 **"검증에 사용한 키에 대응하는 키를 가진 누군가가 이 토큰을 만들었다"** 까지입니다. "우리가 신뢰하는 그 issuer가 발급했다"가 되려면 신뢰하는 `iss`, 그 issuer에 고정된 키(JWKS), 허용 알고리즘, 올바른 `aud`가 **하나의 정책으로 묶여** 있어야 합니다. 검증 키를 토큰이 스스로 고르게 두면 서명은 통과하지만 신뢰는 성립하지 않습니다.

반대로 signature가 보장하지 **않는** 것은 기밀성입니다. payload는 암호화가 아니라 인코딩이라 누구나 Base64URL 디코딩으로 내용을 볼 수 있습니다. 비밀번호·주민번호·카드번호 같은 값을 넣으면 안 되고, 내용 자체를 감춰야 한다면 JWE를 쓰거나 의미 없는 불투명(opaque) 토큰 + 서버 조회 방식으로 가야 합니다.

또 하나, **서명 검증에 성공했다는 것과 이 요청을 허용해도 된다는 것은 다른 문제**입니다. 만료(`exp`), 사용 시작 시각(`nbf`), 발급자(`iss`), 대상(`aud`)을 함께 검증해야 하고 서버 간 시계 차이를 감안한 clock skew 허용치도 필요합니다. 이때 `exp`, `nbf`는 JWT 규격상 필수 claim이 아니므로 "있으면 검사"가 아니라 **애플리케이션 정책으로 반드시 요구**해야 하고, `typ`은 claim이 아니라 JOSE 헤더 파라미터라는 점도 구분해야 합니다. 여기까지 통과해도 계정 정지나 권한 변경 같은 **현재 상태**는 토큰 안에 없기 때문에, 민감한 작업이라면 서버 상태를 한 번 더 확인해야 합니다.

마지막으로 실무에서는 알고리즘 선택보다 **키 관리**가 더 자주 문제가 됩니다. secret/private key 보호, `kid` 기반 회전과 검증 측 캐시 갱신, 유출 시 해당 키 폐기가 되지 않으면 어떤 알고리즘을 골라도 signature가 주는 보장은 사라집니다.

## 꼬리 질문

### JWT payload는 암호화된 건가요?

- 아닙니다. Base64URL **인코딩**일 뿐이라 키 없이 누구나 디코딩해서 볼 수 있습니다. 인코딩은 표현 방식의 변환이고 암호화가 아닙니다.
- 서명이 막아 주는 건 "고치는 것"이지 "보는 것"이 아닙니다. 그래서 payload에는 노출돼도 되는 식별자·권한 수준 정도만 담고, 민감 정보는 넣지 않습니다.
- 내용까지 감춰야 하면 **JWE(JSON Web Encryption)** 로 암호화하거나, 아예 의미 없는 랜덤 문자열(opaque token)을 주고 서버가 조회하는 방식(RFC 7662 introspection)을 씁니다.
- 참고로 서명된 JWT는 payload를 바꿀 수 없을 뿐, **재사용(replay)은 막지 못합니다.** 탈취한 토큰을 그대로 보내는 건 서명 검증을 정상 통과합니다.

### HMAC 방식과 RSA 방식의 차이는 무엇인가요?

- **HS256(대칭)**: 하나의 secret으로 서명하고 같은 secret으로 검증합니다. 발급자와 검증자가 같은 서비스일 때 단순하고 빠릅니다. 대신 검증하려면 secret을 줘야 하는데, **secret을 받은 쪽은 곧 토큰을 위조할 수 있는 쪽**이 됩니다. 그래서 검증 주체가 여럿이면 부적합하고, "누가 만들었는지"를 특정할 수 없습니다.
- **RS256/ES256(비대칭)**: private key로 서명하고 public key로 검증합니다. 공개키는 JWKS 엔드포인트로 배포하면 되고, **검증 권한을 줘도 위조 권한은 주지 않는다**는 게 핵심 차이입니다. OIDC처럼 여러 서비스가 같은 토큰을 검증하는 구조에서는 사실상 이 방식입니다.
- 다만 비대칭이라고 해서 법적·운영적 의미의 "부인방지"까지 보장한다고 말하면 과합니다. 키가 실제로 그 주체에게만 있었다는 전제가 필요하기 때문에, 면접에서는 "검증자에게 위조 능력을 주지 않는다" 정도로 표현하는 게 정확합니다.
- 키 회전 관점에서도 다릅니다. 대칭키는 모든 검증 측에 새 secret을 다시 배포해야 하지만, 비대칭은 새 키쌍의 공개키를 JWKS에 추가하고 `kid`로 구분하면 무중단 회전이 가능합니다.

### `alg: none`이나 알고리즘 혼동 공격은 무엇인가요?

- **`alg: none`**: JWS에는 서명 없는 형태(unsecured JWS)가 규격에 정의돼 있습니다. `none` 자체가 위반이 아니라, **서명이 필요한 자리에서 서버가 이를 받아 주는 구현이 취약점**입니다. 공격자는 header의 alg를 `none`으로 바꾸고 signature를 비운 토큰을 보냅니다.
- **알고리즘 혼동(RS256 → HS256)**: 서버가 토큰이 주장하는 `alg`를 그대로 따르고, RSA 공개키를 HMAC secret으로도 받아들이는 구현일 때 성립합니다. 공개키는 누구나 얻을 수 있으니 그걸 secret 삼아 HS256으로 서명하면 검증을 통과합니다.
- 두 공격의 공통 원인은 **"어떤 키로 어떤 알고리즘으로 검증할지를 토큰이 정하게 두는 것"** 입니다. 대응도 같습니다. 허용 알고리즘 목록만 두는 데서 그치지 말고, **issuer · 키 · 알고리즘 조합을 서버 설정으로 고정**하고 토큰의 header는 그 안에서 `kid`를 고르는 용도로만 씁니다.
- 같은 맥락에서 `jku`, `x5u`처럼 **키를 가져올 URL을 토큰이 지정하는 헤더는 신뢰하면 안 됩니다.** SSRF와 키 주입으로 이어집니다. 키는 서버가 미리 신뢰하기로 한 JWKS에서만 가져옵니다.
- HMAC 비교를 constant-time으로 하는 것도 원칙적으로는 필요하지만, 보통 검증 라이브러리가 처리하는 영역이라 직접 구현하지 않는 한 답변의 핵심은 아닙니다.

### JWT가 탈취되면 어떻게 대응할 수 있나요?

- 탈취된 토큰은 내용을 고칠 필요가 없습니다. **그대로 쓰면 서명 검증을 정상 통과**하므로, 무결성 보장은 이 상황에서 아무 도움이 되지 않습니다.
- 그래서 대응은 "막는다"가 아니라 **"피해 시간을 줄이고 재사용을 어렵게 한다"** 쪽입니다. 전송 구간 보호(HTTPS/HSTS), 짧은 access token 만료, refresh token rotation과 재사용 탐지, 이상 징후 발견 시 해당 사용자 세션 일괄 폐기가 기본 조합입니다.
- 저장 위치도 탈취 경로를 좌우합니다. XSS로 읽히는 곳(localStorage)에 두는지, HttpOnly 쿠키로 두고 CSRF 대응을 별도로 하는지에 따라 위험이 달라집니다.
- 한 단계 더 들어가면 **토큰을 클라이언트 키에 결속(sender-constrained)** 하는 방식이 있습니다. mTLS 기반 결속(RFC 8705)이나 DPoP(RFC 9449)를 쓰면 토큰만 훔쳐서는 재사용이 안 됩니다. 다만 "근본 해결"이라기보다 재사용 제한이고, HTTPS는 여전히 필요합니다.

### Access token과 refresh token은 왜 나누나요?

- **노출 빈도와 취소 가능성의 트레이드오프** 때문입니다. access token은 매 API 요청마다 여러 서비스에 실려 나가고 무상태로 검증되기 때문에 노출은 잦고 취소는 어렵습니다. 그래서 수명을 짧게 가져갑니다.
- refresh token은 auth 서버에만, 재발급 시점에만 전달되므로 노출 빈도가 훨씬 낮습니다. 요청 경로가 한 곳이니 **서버가 상태를 들고 관리하기 쉬워** 폐기가 가능합니다.
- 다만 refresh token이 "자동으로 더 안전한 것"은 아닙니다. 오히려 장기 자격증명이라 탈취 시 피해가 더 큽니다. 그래서 값 자체는 opaque하게 두고 서버에 해시로 저장하며, 사용할 때마다 새 것으로 교체(rotation)하고 **이미 쓴 것이 다시 오면 탈취로 간주해 해당 token family 전체를 폐기**하는 설계를 함께 씁니다.
- 결과적으로 "짧게 살고 검증이 싼 토큰"과 "오래 살지만 통제 가능한 토큰"으로 역할을 나눠, 매 요청마다 DB를 보지 않으면서도 세션을 끊을 수단을 확보하는 구조입니다.

### JWT를 서버에서 강제로 만료시키려면 어떻게 해야 하나요?

- JWT는 검증에 필요한 정보를 토큰이 다 들고 있는 무상태 구조라, **토큰 자체만으로는 조기 만료가 불가능**합니다. 강제 만료를 하려면 어떤 형태로든 서버가 상태를 갖게 되고, 그만큼 무상태의 장점을 일부 포기하는 선택입니다.
- 수단마다 성격이 다릅니다.
  - **짧은 TTL**: 폐기가 아니라 피해 시간 제한입니다. 만료 전까지는 여전히 유효합니다.
  - **refresh token 폐기**: 재발급을 막을 뿐, **이미 발급된 access token은 만료까지 그대로 살아 있습니다.**
  - **`jti` denylist**: 특정 토큰을 콕 집어 무효화합니다. 원래 만료 시점까지는 보관해야 하고, 매 요청 조회가 필요합니다.
  - **`tokenVersion` / 최소 발급 시각(예: `passwordChangedAt` 이후 발급분만 허용)**: 사용자 단위 일괄 폐기에 적합합니다. 사용자당 값 하나만 보면 되니 캐시하기 좋습니다.
  - **introspection(RFC 7662)**: 즉시 정확한 상태를 알 수 있지만 네트워크 의존이 생겨 지연·가용성 비용을 받습니다.
- 서명 키가 유출된 경우라면 개별 토큰이 아니라 **키 자체를 폐기하고 회전**해야 합니다. 해당 `kid`로 서명된 토큰이 전부 무효가 되므로 사실상 전체 강제 만료입니다.
- 실무에서는 보통 "access token은 짧게 + refresh는 rotation과 폐기 관리 + 민감 작업만 서버 상태 확인" 조합으로, 즉시성과 비용 사이에서 타협합니다.

## 한 줄 요약

JWT의 signature는 토큰에 들어 있는 `BASE64URL(header).BASE64URL(payload)` 바이트열에 키와 알고리즘을 적용한 값으로, 그 두 구간이 변조되지 않았다는 무결성과 "검증 키에 대응하는 키를 가진 주체가 만들었다"는 것까지를 보장한다. 기밀성은 보장하지 않으므로 payload에 민감 정보를 넣으면 안 되고, 실제 신뢰는 `iss`·키·알고리즘·`aud`를 하나의 정책으로 고정할 때 성립하며, 서명 검증 성공은 인가가 아니므로 만료·대상·현재 권한 상태를 별도로 확인해야 한다.
