# DB 옵티마이저는 어떤 기준으로 인덱스 사용 여부와 조인 순서를 결정하나요?

> 2026-07-22 · 데일리 면접 질문

## 답변

옵티마이저는 하나의 SQL에 대해 가능한 여러 실행 계획 후보를 만들고, 그중 **비용(cost)이 가장 낮다고 추정되는 계획**을 선택합니다. 대부분의 상용 DB는 이런 비용 기반 옵티마이저(CBO, Cost-Based Optimizer)를 사용합니다.

비용을 추정할 때 근거로 삼는 것은 통계 정보입니다. 테이블의 전체 row 수, 각 컬럼의 cardinality(고유 값 개수)와 값 분포, 인덱스의 깊이와 클러스터링 정도 같은 통계를 바탕으로, 조건절의 **선택도(selectivity)** — 즉 이 조건으로 걸러졌을 때 몇 건이 남을지 — 를 계산합니다. 이 예상 row 수가 인덱스 사용 여부와 조인 순서를 결정하는 핵심 입력값이 됩니다.

**인덱스 사용 여부**는 "인덱스가 있느냐"가 아니라 "인덱스를 타는 게 더 싸냐"로 결정됩니다. 인덱스 스캔은 인덱스를 읽은 뒤 테이블로 다시 접근(랜덤 I/O)하는 비용이 들기 때문에, 조건의 선택도가 나빠서 테이블의 상당 비율을 읽어야 한다면 차라리 순차 I/O로 전체를 읽는 full scan이 더 저렴하다고 판단할 수 있습니다. 그래서 인덱스가 있어도 full scan이 선택되는 경우가 생깁니다.

**조인 순서**도 SQL에 적힌 테이블 순서와 무관하게, **중간 결과(intermediate result)를 최소화하는 방향**으로 결정됩니다. 조건으로 가장 많이 걸러지는 테이블을 먼저 읽어 작은 결과 집합을 만들고, 그걸 기준으로 다음 테이블을 조인하는 식입니다. 이때 각 조인 단계마다 Nested Loop / Hash Join / Sort Merge Join 중 어떤 방식이 싼지도 함께 평가합니다. 예를 들어 driving 쪽 row 수가 적고 반대편에 인덱스가 있으면 Nested Loop, 양쪽 다 크면 Hash Join이 유리한 식입니다.

정리하면, 옵티마이저는 통계 기반의 추정치로 움직이기 때문에 **추정이 틀리면 나쁜 계획을 선택할 수 있습니다.** 그래서 쿼리 성능을 분석할 때는 `EXPLAIN`(가능하면 `EXPLAIN ANALYZE`)으로 실제 선택된 계획을 확인하고, 어떤 인덱스를 탔는지, 예상 row 수와 실제 row 수가 크게 어긋나지 않는지를 확인하는 것이 출발점입니다.

## 꼬리 질문

### 인덱스가 있는데도 full scan이 발생하는 이유는?

- **선택도가 나쁨**: 조건이 테이블의 큰 비율을 반환하면, 인덱스 → 테이블 랜덤 I/O 반복보다 순차 full scan이 더 쌈
- **인덱스를 탈 수 없는 조건**: 컬럼에 함수/연산 적용(`WHERE UPPER(name) = ...`), 묵시적 형변환, 앞쪽 와일드카드(`LIKE '%abc'`)
- **멀티 컬럼 인덱스의 선두 컬럼 미사용**: `(a, b)` 인덱스에서 `WHERE b = ?`만 있는 경우
- **통계 정보가 부정확**: 실제로는 소수 건인데 옵티마이저가 다건으로 추정
- **테이블이 아주 작음**: 몇 페이지짜리 테이블은 그냥 다 읽는 게 빠름

### Cardinality가 낮은 컬럼에 인덱스를 걸면 어떤 문제가?

성별, 상태 코드처럼 고유 값이 적은 컬럼은 조건 하나로 걸러지는 비율이 커서(선택도가 나빠서) 인덱스를 타도 결국 테이블 대부분을 랜덤 I/O로 읽게 됩니다. 옵티마이저가 인덱스를 무시하면 그나마 다행이고, 잘못 타면 full scan보다 느려질 수 있습니다. 그러면서도 쓰기 시 인덱스 유지 비용(INSERT/UPDATE/DELETE마다 갱신)과 저장 공간은 계속 발생하므로, 얻는 것 없이 비용만 드는 인덱스가 됩니다. 다만 값 분포가 심하게 치우쳐 있고 희소한 값만 조회한다면(예: `status = 'FAILED'`가 0.1%) 유효할 수 있어서, 분포까지 봐야 합니다.

### 멀티 컬럼 인덱스에서 컬럼 순서는 어떤 기준으로?

- **등치(=) 조건으로 자주 쓰이는 컬럼을 앞에**, 범위 조건(`>`, `<`, `BETWEEN`, `LIKE 'x%'`) 컬럼은 뒤에 둡니다. 범위 조건 뒤의 컬럼은 인덱스 탐색에 활용되지 못하기 때문입니다
- **선두 컬럼은 단독으로도 자주 조회되는 컬럼**으로 — 선두 컬럼 없이는 인덱스를 (사실상) 탈 수 없으므로, 여러 쿼리 패턴을 커버할 수 있는 순서를 고릅니다
- 같은 조건이라면 **선택도가 좋은(고유 값이 많은) 컬럼을 앞에** 두는 것이 탐색 범위를 빨리 좁힙니다
- 정렬(`ORDER BY`)이나 `GROUP BY` 순서와 맞추면 정렬 비용을 제거할 수 있습니다

### EXPLAIN에서 어떤 지표를 보고 문제를 판단하나요?

- **접근 방식(type/access)**: full scan(`ALL`, `Seq Scan`)이 대량 테이블에서 나오는지, 의도한 인덱스를 탔는지(`key`, `Index Scan`)
- **예상 row 수 vs 실제 row 수**: `EXPLAIN ANALYZE`에서 둘의 차이가 수십~수백 배면 통계가 잘못됐거나 옵티마이저가 오판 중이라는 신호
- **조인 순서와 방식**: 큰 테이블이 driving으로 잡혔는지, 대량 데이터에 Nested Loop가 반복 실행되고 있는지
- **추가 작업 비용**: `Using filesort`(별도 정렬), `Using temporary`(임시 테이블), 인덱스를 탄 뒤 필터로 대량 버려지는 패턴(`rows` 대비 `filtered`가 낮음)
- **실행 시간의 편중**: `ANALYZE` 결과에서 전체 시간의 대부분을 차지하는 노드가 최적화 대상

### 통계 정보가 오래되면 어떤 영향이?

옵티마이저의 모든 판단이 통계에서 나오기 때문에, 통계가 현실과 어긋나면 선택도 추정이 틀리고 → 예상 row 수가 틀리고 → 인덱스/조인 순서/조인 방식 선택이 연쇄적으로 틀어집니다. 대량 배치 적재나 대량 삭제 직후가 전형적인 사례로, 실제로는 수백만 건인데 통계상 수천 건으로 남아 있으면 Nested Loop를 선택해 성능이 급락할 수 있습니다. 그래서 대량 데이터 변경 후에는 통계 갱신(`ANALYZE`, `ANALYZE TABLE`, `DBMS_STATS`)을 해주는 것이 좋고, "어제까지 빠르던 쿼리가 갑자기 느려졌다"면 통계와 실행 계획 변경 여부부터 의심해볼 수 있습니다.

## 한 줄 요약

옵티마이저는 통계 기반으로 각 실행 계획의 비용을 추정해 가장 싼 계획을 고른다. 인덱스는 "있어서"가 아니라 "싸서" 타는 것이고, 조인 순서는 중간 결과를 줄이는 방향으로 정해진다. 추정이므로 틀릴 수 있고, 그래서 EXPLAIN으로 예상과 실제를 대조하는 것이 성능 분석의 기본이다.
