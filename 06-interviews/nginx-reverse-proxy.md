# NGINX를 reverse proxy로 도입한 이유는 무엇인가요?

> 2026-08-04 · 데일리 면접 질문

## 답변

가장 큰 이유는 **애플리케이션 서버가 클라이언트 요청을 직접 받지 않게 하고, 진입점을 한 곳으로 모으기 위해서**입니다. 제 경우에는 Spring Boot 서버를 배포하면서 앞단에 NGINX를 리버스 프록시로 두고, 외부 요청은 모두 NGINX가 받아 내부의 `localhost:8080`으로 `proxy_pass` 하도록 구성했습니다. 이렇게 하면 외부에는 80/443 포트의 NGINX만 노출되고 애플리케이션 서버의 포트나 내부 구조는 드러나지 않으며, 라우팅 규칙을 NGINX 설정 한 곳에서 제어할 수 있습니다.

두 번째 이유는 **공통 처리를 애플리케이션 밖으로 분리**할 수 있기 때문입니다. 대표적인 것이 SSL termination인데, 저는 Certbot으로 Let's Encrypt 인증서를 발급받아 NGINX의 443 포트에서 TLS를 종료하고, 애플리케이션과는 내부에서 HTTP로 통신하게 했습니다. 인증서 발급·갱신이 전부 NGINX 계층에서 끝나기 때문에 Spring Boot 쪽에는 keystore 설정 같은 HTTPS 관련 코드가 전혀 필요 없었고, 80 포트로 들어온 요청을 301로 HTTPS에 리다이렉트하는 것도 NGINX에서 처리했습니다. 같은 방식으로 `limit_req_zone`을 이용해 클라이언트 IP당 초당 요청 수를 제한하고 초과 시 429를 반환하도록 해서, 과도한 트래픽이 애플리케이션에 도달하기 전에 걸러지게 했습니다. gzip 압축, 요청 크기 제한, timeout 설정 같은 것도 마찬가지로 애플리케이션 코드 수정 없이 앞단에서 일괄 적용할 수 있습니다.

세 번째는 **확장성**입니다. WAS를 여러 대로 늘릴 때 `upstream` 블럭에 서버들을 묶고 `proxy_pass`만 upstream으로 바꾸면 NGINX가 요청을 분산해 로드밸런서 역할을 합니다. 클라이언트 입장에서는 진입점이 그대로이기 때문에 뒤에서 서버를 늘리거나 교체해도 영향이 없고, 이 구조는 무중단 배포에도 활용됩니다 — 새 버전을 다른 포트에 띄운 뒤 upstream 대상만 바꿔 reload 하면 트래픽 전환이 됩니다. 여기에 upstream 헬스체크나 failover 설정을 더하면 장애 난 서버로 요청이 가지 않게 할 수도 있습니다.

정리하면, NGINX를 단순히 정적 파일 서버나 포트 포워더로 쓴 것이 아니라 **보안(내부 구조 은닉, TLS, 요청 제한), 운영(공통 설정 일원화, 무중단 배포), 확장(로드밸런싱)을 담당하는 앞단 진입점**으로 도입한 것입니다.

## 꼬리 질문

### Reverse proxy와 forward proxy의 차이는 무엇인가요?

방향이 반대입니다. **포워드 프록시는 클라이언트 쪽에 위치해 나가는 요청을 대리**합니다 — 회사 방화벽처럼 내부 사용자가 외부로 보내는 요청을 감시·차단하는 것이 대표 예시고, 서버 입장에서는 실제 클라이언트가 누군지 가려집니다. **리버스 프록시는 서버 쪽에 위치해 들어오는 요청을 대리**합니다 — 클라이언트 입장에서 실제 어떤 서버가 처리하는지 가려지며, HTTPS 처리·요청 수 제한·로드밸런싱을 하는 NGINX가 대표 예시입니다. 요약하면 포워드는 "클라이언트를 숨기고", 리버스는 "서버를 숨깁니다".

### NGINX가 1대라면 single point of failure가 되지 않나요?

맞습니다. 뒤에 WAS가 아무리 많아도 진입점인 NGINX가 죽으면 전체 서비스가 내려가므로, NGINX 계층 자체의 다중화가 필요합니다. 일반적인 방법은 NGINX를 2대 이상 두고 **keepalived(VRRP) 기반 VIP로 active-standby** 구성을 하거나, **DNS 라운드로빈**으로 여러 대에 분산하는 것입니다. 클라우드 환경이라면 NGINX 앞에(또는 대신) ALB/NLB 같은 관리형 로드밸런서를 두는 것이 가용성을 확보하는 더 흔한 선택입니다. 다만 NGINX는 이벤트 기반 구조라 장비 1대가 감당하는 처리량이 크기 때문에, 규모가 작을 때는 SPOF 리스크를 인지한 상태로 1대 + 빠른 복구 전략으로 시작하고 트래픽/가용성 요구가 커지면 다중화하는 식으로 접근하기도 합니다.

### NGINX에서 upstream 서버로 요청을 분산하는 방식에는 무엇이 있나요?

- **라운드 로빈(기본값)**: 순서대로 돌아가며 분배. `weight`를 주면 서버 성능 차이에 따라 가중치 분배 가능
- **least_conn**: 현재 활성 연결 수가 가장 적은 서버로 — 요청 처리 시간 편차가 클 때 유리
- **ip_hash**: 클라이언트 IP 해시로 같은 클라이언트를 같은 서버에 고정 — 세션을 서버 메모리에 두는 경우의 sticky session 용도
- **hash `<key>`**: URI 등 지정한 키 기반 해시 분배

ip_hash 같은 고정 방식에 의존하기보다, 세션을 Redis 같은 외부 저장소로 빼서 어느 서버로 가도 되는 무상태 구조를 만드는 것이 스케일아웃에는 더 좋습니다.

### SSL termination을 NGINX에서 처리하면 어떤 장점이 있나요?

- **인증서 관리 일원화**: 발급·갱신·설정이 NGINX 한 곳에서 끝나고, WAS가 몇 대로 늘어나도 인증서를 각 서버에 배포할 필요가 없습니다
- **애플리케이션 단순화**: Spring Boot에 keystore 설정 등 TLS 관련 구성이 필요 없어지고, 로컬 개발 환경과 운영 환경의 애플리케이션 설정 차이가 줄어듭니다
- **부하 분리**: TLS 핸드셰이크/암복호화 비용을 프록시 계층이 흡수해 WAS는 비즈니스 로직에 집중합니다
- 주의할 점은 NGINX 뒤에서는 HTTP로 통신하므로 애플리케이션이 원래 요청 정보를 잃는다는 것입니다. `X-Forwarded-Proto`, `X-Forwarded-For` 헤더를 넘겨주고 애플리케이션이 이를 신뢰하도록(Spring의 `ForwardedHeaderFilter` 등) 설정해야 리다이렉트 URL 생성이나 클라이언트 IP 로깅이 어긋나지 않습니다. 또한 내부 구간이 평문이므로 내부망 신뢰가 전제이며, 보안 요구가 높으면 내부 구간도 TLS(re-encryption)를 적용합니다

### NGINX timeout 설정이 너무 짧거나 길면 어떤 문제가 생길 수 있나요?

`proxy_read_timeout` 같은 값이 **너무 짧으면**, 정상적으로 처리 중인 느린 요청(대용량 조회, 배치성 API)을 NGINX가 먼저 끊어 클라이언트에 504를 반환합니다. 이때 백엔드는 요청을 계속 처리 중이라는 게 함정입니다 — 클라이언트가 실패로 보고 재시도하면 같은 작업이 중복 실행될 수 있습니다. 반대로 **너무 길면**, 죽었거나 멈춘 백엔드에 붙은 연결이 오래 유지되면서 클라이언트는 하염없이 기다리고, NGINX와 백엔드의 연결 자원이 고갈되어 장애가 전파·확대됩니다. 그래서 timeout은 "백엔드의 정상 응답 시간 분포"를 근거로 정해야 하고, 애초에 오래 걸리는 작업은 동기 요청으로 붙잡고 있기보다 비동기(작업 큐 + 폴링/알림)로 전환하는 것이 근본적인 해법입니다.

## 한 줄 요약

NGINX를 앞단에 두면 애플리케이션 서버를 외부에 직접 노출하지 않으면서 TLS 종료·요청 제한·공통 설정을 한 곳에서 처리하고, upstream으로 로드밸런싱과 무중단 배포까지 가능해진다. 즉 단순 라우터가 아니라 보안·운영·확장을 담당하는 단일 진입점으로 도입한 것이다.
